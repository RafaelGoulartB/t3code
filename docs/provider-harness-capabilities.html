Por que os comandos dos harnesses não aparecem todos?

T3 Code não incorpora as interfaces de terminal de Codex, Claude Code e OpenCode. Ele é um cliente próprio, que conversa com cada harness por uma API/SDK e traduz a conversa para um modelo comum.

Resposta curta: /compress e /goal não estão ausentes porque o Codex não os suporta. O app-server do Codex já expõe as operações correspondentes. Eles não aparecem porque o T3 Code ainda não criou a ação de produto completa — contrato comum, chamada no adaptador, estado/eventos e controle visual. Já comandos do Claude aparecem porque o SDK dele entrega uma lista de comandos e o T3 consegue apenas inseri-los como texto no prompt.

O que acontece entre a tela e o harness

Composer do T3→ contrato comum→ adaptador do provedor→ API / SDK do harness

Um comando só pode ser mostrado com segurança se todo o caminho o entender. A lista de slash commands da UI é só uma descoberta de capacidades; a execução ainda precisa ter semântica definida para aquele provedor.

O caso do Codex

Função O app-server do Codex oferece? O T3 Code implementa hoje? Consequência
Compactar contexto Sim: thread/compact/start Só recebe thread/compacted A UI informa uma compactação ocorrida, mas não tem botão/comando para iniciá-la.
Meta da thread Sim: thread/goal/set, get, clear Não Não há editor, leitura, limpeza nem projeção dos eventos de meta.
Enviar mensagem Sim: turn/start Sim É o caminho normal da conversa.

No adaptador atual do Codex, sendTurn constrói uma requisição turn/start com texto/anexos. Portanto, digitar /compress chegaria como texto de usuário; não equivale ao comando interno do TUI do Codex. O TUI é outra camada de interface que interpreta atalhos e então chama sua API.

Há uma evidência importante de que a base já está preparada: o pacote de protocolo vendorizado tipa thread/compact/start e todos os métodos thread/goal/*. Falta conectá-los ao domínio do T3.

Por que Claude Code pode exibir mais comandos

Durante a sondagem do Claude, T3 inicia o SDK sem mandar uma mensagem ao modelo e lê a inicialização. Essa inicialização inclui commands; T3 converte-os para slashCommands, remove duplicados e mostra a lista no composer. Ao selecionar um deles, a interface apenas coloca /nome no texto.

Isso funciona porque a integração/SDK do Claude trata esse formato no fluxo de prompt. Não prova que todos os comandos de terminal de todos os harnesses sejam portáveis.

Por que OpenCode e outros podem não ter a mesma lista

A integração do OpenCode nesta base descobre inventário de modelos, variantes e agentes. Ela não popula slashCommands. Assim, o menu fica vazio mesmo que a interface de terminal do OpenCode tenha atalhos próprios: essa informação não é coletada nem existe, aqui, um executor genérico desses atalhos.

Em termos gerais, há três situações:

  • Comando textual encaminhável: o harness declara o comando e aceita /... no prompt. Pode aparecer como no Claude.
  • Operação estruturada: a API oferece um método específico, como compactar ou definir meta no Codex. Precisa de um botão/menu e de uma chamada própria; não deve ser simulada com texto.
  • Recurso exclusivo do TUI: depende de estado local do terminal, menus ou teclas. Só pode ser reproduzido se o harness expuser API/SDK equivalente — caso contrário, não há integração correta a fazer.

Como implementar corretamente no T3 Code

  1. Adicionar capacidades e operações explícitas ao contrato comum (por exemplo, compactThread e operações de meta), sem fingir que são mensagens.
  2. Implementá-las apenas no adaptador Codex usando os métodos tipados do app-server.
  3. Projetar os eventos thread/goal/updated e thread/goal/cleared para o estado e o histórico da thread; o evento de compactação já é parcialmente projetado.
  4. Exibir controles condicionais ao provedor: “Compactar contexto”, editor de meta e estado da meta. Claude/OpenCode esconderiam esses controles até suportá-los.
  5. Testar falhas, reconexão e a atualização assíncrona do estado — especialmente porque compactação e metas mudam a thread, não apenas a tela.

Essa abordagem preserva a prioridade do projeto: comportamento previsível. Uma lista global de “comandos” que envia texto idêntico para todos os providers seria simples, mas acionaria ações diferentes — ou nenhuma — dependendo do harness.

Pontos do código verificados

  • apps/server/src/provider/Layers/CodexProvider.ts: a sondagem do Codex busca modelos e skills, mas não comandos.
  • apps/server/src/provider/Layers/CodexSessionRuntime.ts: o envio normal faz apenas turn/start.
  • apps/server/src/provider/Layers/CodexAdapter.ts: entende a notificação thread/compacted.
  • packages/effect-codex-app-server/src/_generated/meta.gen.ts: o protocolo declara thread/compact/start e thread/goal/*.
  • apps/server/src/provider/Layers/ClaudeProvider.ts: extrai init.commands do SDK do Claude.
  • apps/web/src/components/chat/ChatComposer.tsx: o menu mostra o que houver em selectedProviderStatus.slashCommands e, ao escolher, insere o texto no composer.
